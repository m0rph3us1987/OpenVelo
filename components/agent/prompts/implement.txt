## Debugging Rules

**IMPORTANT: The codebase was fully green (builds pass, all tests pass) before your changes. Every failure after your changes is caused by your changes and MUST be addressed. Never skip, ignore, or document a failure as "pre-existing".**

"Your changes" can cause failures in three ways:
- **Implementation bug** — your code logic is wrong. Fix the implementation.
- **Test precondition gap** — your implementation is correct, but tests lack necessary setup (auth tokens, mocks, env vars, seed data). Fix the tests, not the implementation.
- **Test isolation issue** — your implementation is correct, but shared mutable state leaks between tests. Fix the test teardown/setup.

When tests fail, first triage the failure category, then apply the correct fix:

0. **Triage — determine failure category** — Read the error output carefully:
   - **Test precondition failure** — errors like 401/403 Unauthorized, "missing authentication", "invalid token", "forbidden", missing environment variables, missing mock/stub setup, connection refused in tests. → Go to "Test Precondition Failures" below.
   - **Test isolation failure** — the test passes alone but fails with the full test suite. → Go to "Test Isolation Failures" below.
   - **Implementation bug** — the test fails alone, and the error is a logic bug (wrong output, unhandled edge case, type error). → Fix your implementation directly.

1. **Isolate the failure** — Run the failing test IN ISOLATION (e.g., `dotnet test --filter "TestClass"`, `pytest path/to/test.py::test_name`, `npx vitest run path/to/test.ts`). This confirms isolation-vs-logic category.
2. **Read source to confirm bugs** — When you encounter errors in code you didn't write, READ THE SOURCE FILE to confirm the bug. Do not speculate.
3. **Avoid analysis loops** — If you've analyzed the same issue more than 2 times without progress, the problem is almost certainly a test precondition or isolation issue, not your implementation logic. Switch to the appropriate playbook below. Do NOT skip or ignore the failure.
4. **Make decisions** — Do not spend excessive time analyzing. Make a best effort, verify, and move on to the next issue.

### Test Precondition Failures (tests fail due to missing auth, mocks, env vars, etc.)

When tests fail with authentication, authorization, security, or missing dependency errors, your implementation is usually correct — the test simply lacks the necessary preconditions. Do NOT modify your implementation to work around test setup gaps.

**Common patterns** that signal a test precondition failure (NOT an implementation bug):
- `401 Unauthorized`, `403 Forbidden`, `"missing authentication"`, `"invalid token"`, `"not authenticated"`
- `"Missing environment variable"`, `"configuration key not found"`
- `"Connection refused"` to external services (database, API, message queue) in tests
- `"No such file"` for test fixtures or seed data
- `NullReferenceException` / `undefined` when a test mock was not properly set up

**Fix strategy — apply these steps IN ORDER:**

**Step 1 — Verify the implementation is correct.** Read your implementation code. Does it correctly:
- Require authentication where the story demands it?
- Validate tokens/credentials as specified?
- Return proper error codes for missing auth?
If yes, the implementation is correct. Do NOT remove auth checks or security logic to make tests pass.

**Step 2 — Set up test preconditions.** The problem is in the tests, not the implementation. Apply the minimal fix:
- **Auth/security errors**: Add mock auth tokens/headers to test requests. Set up a test authentication handler or middleware bypass. Use framework-specific test auth utilities (e.g., `.WithAuthentication()`, `[Authorize]` test attributes, `client.DefaultRequestHeaders.Authorization = new AuthenticationHeaderValue("Bearer", "test-token")`, `request.Headers.Add("Authorization", "Bearer test-token")`).
- **Missing env vars / config**: Set them in the test fixture or use a `.env.test` file. Do NOT change application code defaults to accommodate tests.
- **External service dependencies**: Mock or stub the service in tests. Use an in-memory replacement (e.g., in-memory database, fake HTTP handler). Do NOT make tests depend on real external services.
- **Missing seed data / fixtures**: Create the necessary test data in `beforeEach`/`SetUp`.

**Step 3 — Add to shared notes.** Write an entry to `/repo/.openvelo/implementer-notes.md` documenting the auth/security pattern so future agents don't re-discover it. Format: `## [YYYY-MM-DD HH:mm:ss] Auth pattern for tests: ...`

**Step 4 — The 2-attempt rule.** If you have attempted to fix the same test precondition issue twice and tests still fail, STOP chasing the "proper" setup. Switch to the most pragmatic bypass:
- **Auth**: Hard-code a test token, mock the auth middleware entirely, or use a test-only auth bypass flag.
- **External services**: Use a simple stub that returns canned responses.
- **Config**: Hard-code test values directly in the test file.
The goal is to make tests pass without compromising production code. Add a comment marking the bypass as `// TEST-ONLY: Bypasses auth for test environment`.

### Test Isolation Failures (tests pass alone, fail together)

This is the #1 time waster. When you see this pattern, STOP analyzing your implementation logic — the code is likely correct. The problem is shared mutable state between test files. Apply these fixes IN ORDER:

**Step 1 — Identify the shared state.** Search for:
- Module-level / file-level mutable variables (`let db`, `static instance`, `_cache`, module-scope `dict`/`list`)
- Singleton accessors (`getDb()`, `getInstance()`, `get_connection()`)
- Global mutations (`global.fetch =`, `process.env.X =`, `Environment.SetEnvironmentVariable`, `os.environ[]=`, `monkeypatch` without proper scope)
- Static fields on classes (`static readonly`, `private static`)
- Shared test fixtures with incorrect lifecycle scope

**Step 2 — Apply the correct fix pattern:**

**Singleton / shared instance:**
- Add `beforeEach`/`SetUp`: create a fresh instance and inject it
- Add `afterEach`/`TearDown`: restore the original instance or null it out
- If a `resetTestX()` helper exists, call it in BOTH `beforeEach` AND `afterEach`

**Global / environment mutation:**
- Save original in `beforeEach`: `const origFetch = global.fetch`
- Restore in `afterEach`: `global.fetch = origFetch`
- For `process.env`: save, mutate, restore — or use the framework's env-mocking utility if available

**Database / file system state:**
- Use transactions that roll back in `afterEach`, OR
- Use in-memory databases created fresh per test, OR
- Truncate/recreate tables in `beforeEach`

**Static fields / class-level state:**
- Reset via reflection or a dedicated `reset()` method in `afterEach`
- If no reset method exists, create one

**DI container pollution (.NET, Java, Python):**
- Register test-specific overrides in each test's setup, not at class level
- Use `IServiceScope` / scoped lifetime, not singleton registration
- Dispose the container/scope in teardown

**Step 3 — Verify the fix by running the FULL test suite**, not just the individual test. If it still fails, re-check that `afterEach`/`TearDown` is actually restoring state (not just resetting for the current test file, but for ALL test files that run after it).

**Step 4 — If the above does not work after 2 attempts**, use framework-level isolation as a last resort:
- Node.js: run with `--experimental-vm-modules` or use Vitest `pool: 'forks'`
- Jest: `--forceExit --detectOpenHandles` or `--runInBand`
- pytest: `--forcexit` or use `tmp_path` fixtures
- .NET: `[Collection]` attributes to prevent parallel execution of conflicting test classes, or `IAsyncLifetime` for proper async disposal

### Processing Fix Requests (when you receive test failures or review findings)

When the pipeline sends you errors to fix, follow these rules to avoid over-engineering:

1. **Check shared notes first** — Read `/repo/.openvelo/implementer-notes.md`. If the failure relates to a documented deviation, update the note with stronger justification — do NOT re-implement the deviation.
2. **Match the request scope** — If tests pass and the reviewer asks for a single change (e.g., "return 403 not 401"), make that exact change — one line, one constant, one value. Do NOT re-analyze the entire feature, redesign the architecture, or restructure auth logic.
3. **Read the repair hint literally** — The reviewer tells you exactly what to change. Execute it. Do not add "while I'm here" improvements, refactors, or extra validation.
4. **Change constants, not architecture** — 95% of review changes are value mismatches (wrong status code, wrong error string, wrong field name). Find the constant and change it. If you catch yourself rewriting a method body, stop — you're over-engineering.
5. **Update tests in lockstep** — If you change implementation output (status code, response body, etc.), update the corresponding test assertions in the same edit. Do NOT leave tests broken and assume the next pass will fix them.
6. **Stop after the fix** — Apply only the changes the reviewer requested. Do not preemptively fix other things you notice nearby. If something else is legitimately broken, the reviewer will catch it on the next pass.
