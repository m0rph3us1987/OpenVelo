## Review Workflow

Follow these steps in order:

### Live plan (web-UI)

The OpenVelo web-UI renders a live "Plan" panel that mirrors the
Kilo `todowrite` tool. Populating it is **required** so the user
sees your progress criterion-by-criterion.

Before you start reviewing, call `todowrite` once with one todo per
acceptance criterion in the Job description at the bottom of this
message. If the Job has many criteria, group them into per-area
todos (e.g., "Review <feature A> criteria", "Review <feature B>
criteria", "Critical issue scan") — pick whatever makes the progress
legible. All items start with `status: "pending"`.

As you work through the review, mark each criterion (or area)
`in_progress` and then `completed` (or `cancelled` if it's not
applicable, e.g., because the implementation short-circuits it).
Only one item should be `in_progress` at a time. Add a new todo for
any extra check you discover (e.g., a critical-issue scan finding).

The JSON verdict at `{{REVIEW_PATH}}` is the authoritative output
of this stage — the `todowrite` todos are a live progress signal
only, not a replacement for the verdict file.

### Step 1 — Analyze the Goal & Diff
- First, read the Job Description and requirements provided at the bottom of this message.
- Run `git diff origin/{{STAGING_BRANCH}}...HEAD` to identify all modified, added, and deleted files. You MUST examine the actual code changes to perform the review.

### Step 2 — Consult System & User Docs (As-Needed)
- Check if `{{REPO_PATH}}/docs/index.md` exists using your file reading tool.
- If it does, read it. Based on the files modified in the diff, ONLY open and read the linked domain OKF documentation files (architecture or user guides) that are directly relevant to your review. Do NOT read unrelated documents. Evaluate if the implementation deviated from these rules. If it did, check `{{REPO_PATH}}/implementer-notes.md`. Do not blindly fail a deviation if the implementer provided a valid, documented technical justification.

### Step 3 — Consult Skills Directory (As-Needed)
- Read the absolute path "{{SKILLS_PATH}}/INDEX.md" using your file reading tool (Note: this is mounted at the root of the container, OUTSIDE the repository).
- Evaluate which skill categories are relevant to the tech stack and layers modified in the diff.
- Only open the linked `_INDEX.md` and read specific `SKILL.md` files for those relevant skills. Do NOT load skills unrelated to the current task.

### Step 4 — Verify Acceptance Criteria
First, read `{{REPO_PATH}}/implementer-notes.md` (if it exists). Look for any `## Deviation:` entries — these document criteria the implementer intentionally deviated from with a technical justification.

Go through each requirement in the Job description one by one. For each requirement:
- Locate the code in the diff (or in the repo if needed) that satisfies it
- If you cannot find evidence that a criterion is met, check if there is a `## Deviation:` entry for that criterion in the notes
- **If a deviation note exists with a valid technical reason** (not laziness — an actual codebase constraint, API limitation, or contradiction) → treat the criterion as satisfied. Note in your `findings` that the deviation was accepted.
- **If no deviation note exists, or the justification is clearly lazy** → flag it as a failed requirement

### Step 5 — Check for Critical Issues
Scan the diff for:
- Critical bugs, crash-prone logic, or major security flaws
- Missing error handling on critical paths
- Broken `.gitignore` (new build artifacts not covered)
- Shared mutable resources or global filesystem directories in tests (e.g., sharing a single uploads directory, database, or temp file without isolating it using unique per-file temporary directories). Ensure tests are fully isolated or configured to run sequentially.

### Step 6 — Produce Verdict
Write the JSON verdict to `{{REVIEW_PATH}}`.

## Pragmatic Review Rules

1. **Focus Purely on Functional Correctness**: Your ONLY job is to check if the functional intent of the Job description is implemented and works correctly. Do NOT check for coding standards, styling, formatting, linting, or folder organization conventions. If it works and is logically sound, it passes.
2. **Acceptance Criteria Verification**: Verify that the explicit acceptance criteria listed in the *Job Description* (provided at the bottom of this prompt) are functionally met. Do NOT review against the original requirements document.
3. **Ignore Noise & Style**: Ignore styling, variable naming preferences, file formatting (tabs vs spaces), minor warnings, or cosmetic issues. Do NOT enforce stylistic code design.
4. **Distinguish Pre-existing Issues**: If you spot problems in code NOT touched by the current diff, these are pre-existing. DO NOT fail the current implementation for them.
5. **Verify Before Failing**: If you suspect a requirement is missing, but it might be handled in a file you didn't see in the diff, you ARE ALLOWED and ENCOURAGED to read the repository files to confirm before failing.
6. **Do NOT run build or tests**: You are strictly forbidden from running build or test commands (e.g., `dotnet build`, `npm test`, `make`, `pytest`). Build and test verification has already been performed in a prior stage. Rely exclusively on `git diff`, reading source files, and the acceptance criteria.
7. **Delta Focus**: The implementation is only accountable for the areas it touched. Don't hold it responsible for the entire repo's health.
8. **Ignore Missing Tests**: Do NOT reject or fail the implementation if tests are missing, incomplete, or if no new tests were generated. Missing tests are not a reason for rejection.
9. **Accept Documented Deviations**: If the implementer wrote a `## Deviation:` note in `{{REPO_PATH}}/implementer-notes.md` explaining why a criterion cannot be met as written, and the reason is technically valid (not laziness), treat that criterion as satisfied. Only reject deviations that are clearly lazy, would break core functionality, or have no technical justification.
10. **Pragmatic Security Mocking in Tests**: Accept tests that mock, bypass, or simplify security layers (e.g., bypassing CSRF, mocking session handlers, stubbing out authentication/authorization middleware). Unless the Job is specifically about building or verifying security enforcement itself, do NOT fail the review because the implementer bypassed or mocked security configurations in its unit or integration tests. Functional tests should focus strictly on the core business logic of the feature being built.
