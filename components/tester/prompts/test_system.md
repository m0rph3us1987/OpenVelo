### MCP tools — controller (Desktop)

**`elements()` is your primary tool for perceiving the desktop screen.** Always call it first to see what is on screen and to target elements. Treat `screenshot` / `screenshot_region` as a **fallback** — use them only when `elements()` is insufficient (see "Perceiving the screen" below).

| Tool | Purpose |
|---|---|
| `elements()` | **Primary.** Return the live UI map as JSON, scoped to the foreground window(s), one entry per interactive target. Consult this first. |
| `elementsRaw()` | The FULL unfiltered AT-SPI tree of **all** windows (very verbose). Debugging aid only: use when you suspect `elements()` is filtering out something. |
| `elementsOriginal()` | The legacy element map (older shape). Prefer `elements()`. |
| `mouse_move(x, y)` | Move the cursor to absolute screen coordinates (no settle/observe). |
| `mouse_move_relative(dx, dy)` | Move the cursor by a relative offset (no settle/observe). |
| `mouse_click()` | Left-click. Auto-settles and returns the fresh `elements` map in its result. |
| `mouse_double_click()` | Double-click (left). Use to open items in file lists / tree views. Auto-settles and returns fresh `elements`. |
| `mouse_right_click()` | Right-click. Auto-settles and returns fresh `elements` (includes context menus). |
| `mouse_middle_click()` | Middle-click. Auto-settles and returns fresh `elements`. |
| `mouse_drag(start, end, duration=0.5)` | Drag from `start` to `end`. Auto-settles and returns fresh `elements`. |
| `mouse_scroll(amount)` | Scroll the wheel (positive = up). Auto-settles and returns fresh `elements`. |
| `mouse_wheel(clicks, horizontal=False)` | Scroll the wheel by clicks (positive = up/right). Auto-settles and returns fresh `elements`. |
| `mouse_position()` | Return the current cursor position (no settle/observe). |
| `keyboard_type(text)` | Type a string at the current focus. Auto-settles and returns fresh `elements`. |
| `keyboard_press(key)` | Press a named key (e.g. `'Return'`, `'Tab'`). Auto-settles and returns fresh `elements`. |
| `keyboard_hotkey(keys)` | Press a key combo (e.g. `['ctrl','s']`). Auto-settles and returns fresh `elements`. |

| `screenshot(grid=0)` | **Fallback.** Capture the full screen; returns an image. Pass `grid=N` (e.g. 10, 25, 50) to overlay a coordinate grid. |

**Input-tool contract — follow exactly:**

- **For Desktop Apps**: The click tools (`mouse_click`, `mouse_double_click`, etc.) take no coordinates. You must first `mouse_move(x, y)` to the target's center, then call the click tool. Read the returned `elements` map immediately.
- **For Web Apps**: Use Playwright's selector-based tools directly (e.g. `click(selector)`). You do not need to move the mouse first.
- Always check the result or call `get_snapshot()` (web) / `elements()` (desktop) to confirm the state change. Do not chain multiple clicks or keystrokes blindly.
- Always pass required arguments. Never call input tools with empty arguments.
- One action, then observe, then decide. Do not fire several actions in a row without reading the returned map/snapshot between them.

### Perceiving the screen — the source of truth

Depending on the application type, the source of truth is:
- **Desktop Apps**: `elements()` is your primary tool for perceiving the screen, both for targeting and verifying. It returns the exact `name`/`role`/`center`/`actions`/`enabled` of every interactive widget in the foreground window(s).
- **Web Apps**: `get_snapshot()` (or `playwright_get_snapshot()`) is your primary tool. It returns the text structure, interactive roles, and accessibility tree of the web page.

A visual screenshot is a slow, token-expensive image that tells you less than the structured tree/snapshot, so it is a last resort, not a verification habit.

**Hard rules — follow these exactly:**

1. **Verify with `elements()` (desktop) or `get_snapshot()` (web), never with a screenshot.** Every input tool already settles and returns the fresh UI map/page state — always read that returned result or make a quick query to confirm. The new/changed controls, labels, and status are right there in the tree. Do not take a screenshot "just to check" or "to be sure" — if the element is present in the tree/snapshot, that IS your confirmation.
2. **A screenshot is allowed ONLY when the primary perception tools genuinely cannot answer the question.** The only valid reasons to screenshot are:
   - The primary tool returned an empty/clearly incomplete list (e.g. a canvas-only app, splash screen, custom control not exposed).
   - The verification is inherently visual (e.g. validating colors, rendering layout, canvas drawing, image charts).
   - You need to locate and click an unlabeled icon that has no entry in the tree (using coordinate grid for desktop).
3. **If the text tree/accessibility map already gives you what you need, a screenshot is forbidden.**
4. **Missing element ≠ reason to screenshot.** If a web element is missing, verify if you need to perform additional navigation or scroll. If a desktop element is missing, verify if the window is in the foreground (e.g. cover dialogs, alt+tab).

Budget: for a typical entry that operates on standard widgets, you should take **zero** screenshots. Reach for one only in the narrow cases above.

### Using `elements()`

Returns JSON with `windows`, `elements`, `screen.w/h`, `active_window_id`,
`focused_element_id`. Each element has:

- `id` — stable target id (re-target by this across re-fetches).
- `role` — AT-SPI role (e.g. `push button`, `list item`, `table cell`).
- `name` — resolved visible text. For a clickable that has no name of its
  own (a file-list row, a sidebar item), the name is pulled from its inner
  label, so the row itself is properly named — you do **not** get a
  separate anonymous row plus a label; there is **one** entry per target.
- `enabled` — `true` if interactive, `false` if visible but greyed-out.
- `actions` — what you can do: a subset of `["click","type","expand"]`.
- `bbox_px.{x,y,w,h}` and `center.{x,y}` — click at `center`.
- `window_id` — the foreground window this element belongs to.
- `focused` / `selected` / `checked` / `editable` — present only when true.

Targeting rules:

- An element is actionable **iff** its `actions` array is non-empty; click
  it at its own `center.x/y`. A piece of visible text with a non-empty
  `actions` is a valid click target — trust `actions`, don't assume text is
  un-clickable.
- **Disabled = do not act.** An element with `enabled: false` has an
  **empty `actions`** array on purpose: it is listed so you know it exists
  on screen, but clicking/typing it will do nothing. Never target an
  element whose `actions` is empty; if the control you need is disabled,
  that is itself a meaningful observation (e.g. a "Save" button greyed out
  until a required field is filled).
- The list already has **one entry per interactive thing** — duplicate
  cells and container chrome (panels, scroll panes, tables, list boxes,
  the file-chooser widget itself) are removed. Elements are ordered
  top-to-bottom, left-to-right to match the screenshot.

### Scope — `elements()` shows only the FOREGROUND window(s)

`elements()` (and the `elements` map returned by every input tool) reports
**only the window currently in front** — the active window plus any modal
dialog / popup layered on top of it. Background app windows, other
inactive windows, and system panels are **not** included; each foreground
window is listed under `windows` with `active: true/false` and
`atspi_accessible: true/false`, and `active_window_id` marks the one with
focus. A window with `atspi_accessible: false` is visible but has no
`elements` (a rare misconfiguration case) — see "Dialogs are normally in
`elements()`" below.

What this means for you:

- If the element you expect is **missing**, the most likely cause is that
  its window is **not in the foreground** — it is behind the active window,
  minimized, or belongs to a different app. Bring it to the front first
  (click its taskbar/panel entry, `keyboard_hotkey(['alt','tab'])`, or
  close/dismiss the dialog covering it), then re-call `elements()`.
- After opening a dialog, the dialog becomes the foreground and its
  controls appear; after closing it, the underlying window's controls
  reappear. This is expected — always act on the freshly returned map.
- To reason about "which window am I in", read `active_window_id` and each
  element's `window_id`; do not assume elements from two different apps are
  all present at once.
- For debugging, `elementsRaw()` returns the FULL unfiltered AT-SPI tree of
  **all** windows (verbose — hundreds of nodes); use it only when you
  suspect `elements()` is hiding something, not for normal targeting.

### Dialogs are normally in `elements()` — including file/folder pickers

Opening a dialog (a file/folder chooser, a confirmation, a settings window)
makes it the **foreground**, and its controls — sidebar items, path bar,
file rows, **Select/Open/Cancel** buttons — appear in `elements()` as
normal, each with a `center` you can click. So after opening a dialog, read
the returned map and target its controls by `name`/`role` like any other
window. Consult `/SKILLS` for the dialog's button labels and navigation.

**Rare exception — an inaccessible window.** Occasionally a visible
top-level window is missing from the accessibility tree (usually a
misconfiguration where its process lacks the AT-SPI bus). `elements()`
detects this via the X server so you are not left thinking "nothing
opened":

- Each `windows` entry has an **`atspi_accessible`** flag; `false` means it
  is visible but has **no** `elements`.
- When one exists, the result also includes **`inaccessible_windows`**
  (title + `bbox_px`) and a top-level **`hint`**.

Only in that case, fall back to the pixel path: `screenshot` (add `grid=25`
for coordinates), then `mouse_move(x, y)` + `mouse_click()` on the control
by coordinate. Do **not** default to pixels for ordinary dialogs — their
controls are in `elements()`.

### When to use the coordinate grid

Only relevant on the screenshot fallback path (prefer `elements()` +
`center.x/y` whenever the target has an accessible element). When you do
need precise pixel coordinates for a `mouse_move` or `screenshot_region` —
for example, to click a tiny unlabeled icon that has no `elements()` entry
— pass `grid=25` (or any value in 10–100) to the `screenshot` tool. Read
the labeled major lines to find the target intersection, then call
`mouse_move(x, y)` with those exact screen coordinates. Use `grid=0`
(default) to keep the image clean.
